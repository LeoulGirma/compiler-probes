Rust · Go · C# · four sets of tests

A 7.3× gap in a loop. Just 1.05× with a database.

So when does faster code actually make a faster service? We followed the question from the machine instructions a compiler emits to a payment API in containers, testing Rust, Go, .NET 10, .NET 11 RC2 and Native AOT.

The two ratios measure different things: time per array element, and median request latency with a database in the path. They show why context matters, not that every language performs the same.

Three results we did not expect

Where the tests pushed back

The findings that break a simple story. Each one is documented in full on its page.

Same runtime, opposite results

.NET 11 RC2 used about 11% more CPU per request than .NET 10 in the plain in-memory API, and 26% less in the payment service. One workload does not predict another.

Set 3 →Set 4 →

Fewer instructions, slower code

.NET 11 turns Math.BigMul into a single multiply instruction, cutting the loop from 25 to 20 instructions, and the loop runs 31% slower: the running total now spills to the stack.

Read the listing →

One run that hung

In one of five rounds, .NET 10 Native AOT stopped answering during the provider outage: 14,812 requests timed out at low CPU. Three repeats with extra diagnostics were clean; the cause is still open.
