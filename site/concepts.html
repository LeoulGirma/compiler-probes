Getting to machine code

Ahead-of-time vs just-in-time

Rust and Go compile to machine code at build time. C# ships IL and the runtime's JIT compiles it while the program runs.

Why it mattersRun-time compiling costs CPU at start-up but can optimise for the traffic it actually sees.

Tiered compilation

The JIT first compiles each method quickly (Tier 0), then recompiles the hot ones with full optimisation (Tier 1).

Why it mattersUntil hot code reaches Tier 1, the service is slower and uses more CPU. Here that took about 90 s under load.

Set 1 →Set 4 →

Dynamic PGO

Before Tier 1, the JIT records which types and branches really occur, then specialises the code for them. On by default since .NET 8.

Why it mattersIt is why warm JIT code can beat ahead-of-time code.

Set 1 →Set 4 →

ReadyToRun

A publish option that ships precompiled code next to the IL, so less starts at Tier 0.

Why it mattersShorter start-up and warm-up, PGO kept, bigger binaries.

Set 1 →Set 2 →

NativeAOT

Publishes the app as one native executable: no IL, no JIT, unused code removed.

Why it mattersGo-like start-up and memory, no warm-up. No PGO, and reflection-heavy libraries need source generators.

What optimisers do

SIMD vectorisation

Using CPU instructions that process 4–16 numbers at once.

Why it mattersA loop can get 4–8× faster with no source change. LLVM does it automatically; in C# you ask for it with Vector<T>.

Set 1 →

Bounds-check elimination

Deleting an array index check when the compiler can prove it always passes.

Why it mattersLeftover checks cost a branch each and block vectorisation.

Set 1 →Set 2 →

Devirtualisation

Replacing an interface or virtual call with a direct, often inlined, call when the type is known.

Why it mattersAbstractions become nearly free when the compiler can see through them.

Set 2 →

Runtime async

In .NET 11 the runtime, not a compiler-generated class, tracks where an async method paused.

Why it mattersAwaits that finish immediately get 4× cheaper and stop allocating. Off by default in RC2.

Set 2 →

Register spills

When values do not fit in CPU registers, the compiler parks them in memory and reloads them.

Why it mattersFewer instructions can still be slower. Only timing tells.

Set 2 →

Memory

Garbage collection

C# and Go free unused memory automatically by pausing or running a collector. Rust frees memory when its owner goes away.

Why it mattersCollections show up as latency spikes and as memory headroom.

Set 3 →

Footprint

Memory held before any traffic, and the size of the image a node must pull.

Why it mattersIt decides how many instances fit on a node and how fast a new one can start.

Set 4 →

Reading the numbers

Percentiles

p50 is the median. p99 means 1 request in 100 was slower than this.

Why it mattersUsers feel the tail: a page that makes 20 backend calls hits their p99 on about 1 load in 5.

Set 3 →Set 4 →

Open-loop load

Requests are sent on a fixed schedule and timed from when they were due, as real traffic would be.

Why it mattersTests that wait for each answer hide stalls. See the drawing below.

Cold start

Time from launching the process to its first answered request.

Why it mattersIt sets how fast you recover from a crash and scale out.

Set 4 →

CPU limits

A one-CPU container gets one core's worth of time per second. 100% means all of it.

Why it mattersCPU per request is a large part of compute cost, alongside memory, instance size and how capacity is billed. At the limit, extra work turns into queueing and latency.
