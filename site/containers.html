Compiler probes · set 4 · production-shaped

The same payment service, in containers, with real moving parts

Each service checks a JWT, rate-limits in Redis, validates the payment, records it in Postgres, charges a mock provider that is slow 1% of the time, captures it in a transaction with the merchant balance, logs a JSON line and replies. Each runs alone in a Linux container capped at 1 CPU and 512 MB. The provider is a mock with injected delays and failures: a realistic simulation, not a deployed system.

JWT→Redis rate limit→validate→INSERT pending→provider call · 1 s timeout→tx: capture + balance→JSON log + reply

The answer

With a database and a provider in the path, medians converge at 28–30 ms. C# needs about 90 s under load to warm up and more CPU per payment; Native AOT removes the warm-up but not the CPU cost. Every build survived a simulated provider outage with its ledger intact.

The question

What changes with Postgres, Redis, a flaky provider and a one-CPU container?

No retry storms, no queue that outlives the outage, no crash. Failed payments are marked failed in the database, never left pending.

AOT takes away everything that comes from compiling at run time: start-up is 2.2× faster and level with Go and Rust, there is no 90-second warm-up, and the cold-start tail is as short as theirs. It does not make the steady-state work cheaper. Settled CPU is the same as the JIT build, and .NET 11's peak throughput is 6% lower, because the JIT's profile-guided recompilation does a little better than ahead-of-time code once it has warmed up. That gap is small: across those five rounds the AOT build's peak varied by about 3% and the JIT build's by under 1%, but two later rounds (below) saw AOT's peak swing by 12–14%, so treat it as indicative. .NET 11 stays cheaper than .NET 10 under AOT too.

One run went wrong. In the second of 5 rounds, .NET 10 AOT stopped answering during the provider-outage test. It had already slowed to a 1.5–2 s median for ten seconds before the outage began; then, about 30 seconds after the outage began, nearly every request waited out the 10-second client timeout (14,812 in all), while its CPU fell to about 30% and memory rose to 204 MB. It stayed up, the ledger stayed consistent, and the next three rounds were clean, with database connection states and service logs recorded and nothing unusual in either. Low CPU while unresponsive suggests something blocked rather than overloaded, but one episode in 5 runs is not enough to pin it on NativeAOT.

Tuning the AOT build did not change the cost. Two more rounds added AOT builds published with OptimizationPreference=Speed and IlcInstructionSet=native, which compile for this exact CPU instead of a generic x64 baseline. CPU at 500 payments a second stayed within a few points of the default AOT build (.NET 10: 57% → 60%, .NET 11: 54% → 52%), and start-up, memory and latency did not move. Peak throughput rose 12% for .NET 10 (1,332 → 1,493/s) and 1% for .NET 11, but default AOT's own peak moved by up to 14% between these two rounds, so neither change is clearly real. The likely reason is that this service spends its CPU in networking, the database driver and the framework rather than in tight loops of its own, which is where these flags help.

How this was measured, and what it still leaves out

Same work everywhere

ASP.NET Core minimal API with JwtBearer, Npgsql, StackExchange.Redis and HttpClient; Go's net/http with pgx, go-redis and golang-jwt; Rust's axum with tokio-postgres, redis, reqwest and jsonwebtoken. Each uses a 32-connection database pool, releases it during the provider call, and returns byte-identical signatures for the same payment.

The load

A Go load generator inside the Docker network, with a fresh payment id per request, a JWT per merchant, 2% invalid payments (422) and 1% repeated ids to exercise idempotency. Requests go out on a fixed schedule and are timed from when they were due, so queueing inside a service is counted.

Isolation

Docker Desktop's VM has 4 CPUs: the service gets 1, Postgres 1.5, the load generator 1, the provider 0.5 and Redis 0.25. Only one payment service runs at a time, against an emptied database. The C# builds publish self-contained for Alpine with default settings (server GC, tiered PGO).

Still missing

One machine and one laptop CPU underneath Docker, so container CPU is shared with Windows; no real network between services; one replica, no load balancer;, and a deliberately small schema. The next step that would matter is running this harness against a real service's hot endpoint.

.NET 11 is a release candidate (RC2); numbers can change by GA.
