One payment API, seven builds, one laptop

The same small payment API, written in C#, Go and Rust, built seven ways and load-tested on one laptop. It parses a JSON payment, validates it, signs it with HMAC-SHA256, records it in an in-memory ledger and replies in JSON. Throughput is closer than the language arguments suggest: the slowest build reaches 79% of the fastest. The bigger differences are memory, CPU per request, tail latency and how each runtime copes with a heap under pressure.

The answer

Throughput is close: the slowest build reaches 79% of the fastest. The real differences are CPU per request, memory and tail latency. Here .NET 11 RC2 used about 11% more CPU per request than .NET 10, the opposite of what set 4 found.

The question

How close are the languages when they serve a real API, with no database in the way?

A heap under pressure

A separate program keeps one million small orders alive (about 150 MB), then for 10 seconds allocates 200 short-lived orders and replaces 20 random long-lived ones per loop. Every loop is timed, so a pause shows up the way a request handler would feel it. Writing new objects into an old, large array is the hardest case for a generational collector, so treat this as a stress test, not a typical service.

.NET's server GC finishes the most work and has the best p99.9, but every collection stops the program: 108 collections in 10 seconds, about 42 ms each on average and up to 115 ms. Workstation GC collects 13× more often in smaller pieces: shorter worst case, but a slow p99.9 and half the throughput. .NET 11 behaves the same as .NET 10 here.

Go reports only 27 ms of stop-the-world time over the run, yet the loop still stalled for up to 37 ms: Go makes allocating code help with marking while a collection runs, and that work lands on the request path. Rust has nothing to pause, but freeing and allocating through the Windows heap makes it the slowest at this particular churn.

How this was measured

The service

ASP.NET Core minimal API with source-generated JSON (so the same code builds for NativeAOT), Go's net/http with encoding/json, Rust's axum with serde. Each awaits an in-memory ledger call that completes immediately, as a cache hit would. All three return byte-identical signatures for the same request.

Isolation

Each server starts suspended, is pinned to logical CPUs 0–3 (two physical cores), then resumed, so every runtime sizes its thread pool for two cores. The load generator, a raw-socket Go client, runs on CPUs 4–5; 6–7 stay free for Windows. On 2 CPUs it pushed as many requests as on 4, so it is not the bottleneck.

Rounds

Three rounds in a rotating order, 30 s rest between servers, CPU clock logged throughout (it never dropped below 3.3 GHz). Medians across rounds; run-to-run spread on throughput was up to 15%.

Limits

One Windows laptop over loopback, so no network latency and no Linux: production containers can rank differently, especially for GC and threading. Start-up time is not reported, because Windows waits about half a second before retrying a refused local connection, which hides the differences.

Service, load generator, GC stress and driver: work3/ (cs, go, rust, loadgen, gc, workload3.py). .NET 11 is a release candidate.
