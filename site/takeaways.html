What the numbers mean for a service

Based on the container service in set 4: JSON over HTTP, a database, one downstream call to a simulated provider. Treat these as results for workloads shaped like it.

If this is your situation

Scale out often, scale to zero, short jobsNativeAOTReady in 0.47 s and full speed from the first request. Check library support; build on Linux.
Long-lived service at high loadJIT (default)Same CPU as AOT once warm and about 6% more peak throughput (consistent across rounds). Hold readiness until warm, or add ReadyToRun.
Pack many instances per nodeNativeAOT, or GoIdle: Rust 0.7 MB, Go 5 MB, C# AOT 19 MB, C# JIT 32 MB.
Planning the .NET 11 upgradeTest on RC2 now−26% CPU in the container service. On many cores, check the new thread-pool spin default (DOTNET_ThreadPool_UnfairSemaphoreSpinLimit). Recheck hot numeric loops.
Latency dominated by a database or another serviceKeep your stackEvery build had a 28–30 ms median and failed the same way. Tune pools and timeouts instead.

What holds across all four sets

Each compiler wins where its bet paysLLVM: loops. RyuJIT: dynamic calls. Go: predictability.
Realism compresses differencesMedians converge; start-up, memory and the tail do not.
Defaults move resultsRuntime async off, PGO on, server GC on, and .NET 11's thread-pool spin limit.
Read the machine codeIt explained every claim that failed.

How the numbers were made

One Intel i5-10300H laptop (4 cores, 8 threads), Windows 11, plugged in, nothing else running. Set 4 runs in Docker Desktop's Linux VM with 4 CPUs; each service gets 1 CPU and 512 MB.

Out-of-the-box settings: cargo --release, go build, C# Release with server GC and tiered PGO. Opt-ins (runtime async, NativeAOT, Go PGO) are separate, labelled builds.

Medians of repeated rounds. In sets 1–3 single runs varied by up to about 10%, so smaller gaps there are noise. Set 4 repeated each build in 2–5 rounds; a gap counts only when it is larger than the spread between those rounds (for example the 6% AOT vs JIT throughput gap, where rounds varied by 3% or less). Two one-off stalls did not recur and are reported as such.

Set 4 is a realistic simulation, not a deployed system: the payment provider is a mock with injected delays and failures, and everything runs on one machine.

.NET 10 (10.0.12 for the JIT builds), .NET 11.0.0-rc.2, Go 1.27.2, Rust 1.99.0, Postgres 17, Redis 7.
